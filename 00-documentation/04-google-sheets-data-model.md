# 04 — Google Sheets Data Model

## 1. Purpose

This document is the authoritative specification for the Google Sheets database used by the Student Management Dashboard. The backend must follow these schemas, identifiers, relationships, and integrity rules. Other documents may describe behavior, but must not redefine these columns independently.

The database is one private Google Spreadsheet with a fixed set of tabs. The React frontend never accesses this spreadsheet directly; all reads and writes go through the authenticated Google Apps Script API.

## 2. Data-model principles

1. Keep the model normalized enough to preserve history without making routine administration complicated.
2. Give every record a stable backend-generated ID. Never use row numbers, names, phone numbers, or spreadsheet positions as IDs.
3. Store one fact in one authoritative place. Derive balances and summaries from underlying records instead of maintaining duplicate manual totals.
4. Keep financial transactions and class-session history append-oriented. Correct errors through explicit, auditable correction or void operations.
5. Archive students and deactivate obsolete links; do not hard-delete historical records through normal application workflows.
6. Use explicit enums and validation rules. Do not rely on free-form status spelling.
7. Resolve columns by validated header names, not hard-coded column letters.
8. All foreign-key relationships and ownership rules are checked by the backend before a write.
9. Preserve source references during migration so imported data can be reconciled.
10. Avoid speculative fields. Add a column only when a documented product requirement needs it.

## 3. Spreadsheet-wide conventions

- Spreadsheet timezone: `Asia/Kolkata`.
- Display currency: `INR` for Version 1.
- Date display: `DD MMM YYYY`.
- Date-time display: `DD MMM YYYY, HH:mm` in `Asia/Kolkata`.
- IDs: strings generated by the backend, with entity-specific prefixes where useful.
- Boolean cells: actual boolean values, not free-form strings such as `yes`, `Y`, or `true`.
- Monetary cells: numeric values, never strings containing currency symbols or commas.
- Optional values: blank when absent; do not use inconsistent placeholders such as `-`, `N/A`, or `unknown`.
- Timestamps: store a consistent, documented timestamp representation and convert to local display time in the application.
- Enumerations: store the exact uppercase values listed in this document.
- Header row: row 1 of every tab.
- Data rows: begin at row 2.

The backend must not assume that a blank row means the end of a dataset. It must handle empty tabs and gaps safely.

**Purpose:** Track purchased class allocations separately from financial transactions.

| 1 | `package_id` | String | Yes | Unique, immutable ID |
| 2 | `student_id` | String | Yes | References `Students.student_id` |
| 3 | `enrollment_id` | String | No | If supplied, must belong to the same student |
| 4 | `package_name` | String | Yes | Human-readable label |
| 5 | `purchased_classes` | Integer | Yes | Positive integer |
| 6 | `package_price` | Number | No | Package price in the configured currency |
| 7 | `currency` | String | Yes | `INR` in Version 1 |
| 8 | `purchase_date` | Date | No | Date the package was agreed/purchased |
| 9 | `start_date` | Date | No | Optional package validity start |
| 10 | `expiry_date` | Date | No | Optional; must not precede `start_date` |
| 11 | `package_status` | Enum | Yes | `ACTIVE`, `EXHAUSTED`, `EXPIRED`, `CANCELLED`, `CLOSED` |
| 12 | `notes` | String | No | Optional operational context |
| 13 | `created_at` | Timestamp | Yes | Set by backend |
| 14 | `updated_at` | Timestamp | Yes | Set by backend |
| 15 | `closed_at` | Timestamp | No | Set when package is closed |

Rules:

- `purchased_classes` is the original allocation and must not be edited to conceal class consumption.
- `package_price` is not a payment record.
- The remaining balance is calculated from the original allocation, eligible class consumption, and explicit class-credit adjustments if those are supported.
- A package may be linked to an enrollment. When linked, both records must belong to the same student.
- Do not automatically create a package from a payment unless the business workflow explicitly requires it.
- Do not count scheduled, cancelled, or rescheduled sessions as consumed classes by default.
- Expiry and cancellation behavior must follow Document 05.

Initial calculation:

`remaining_classes = purchased_classes - consumed_classes + credited_classes`

`consumed_classes` and `credited_classes` must be derived from valid, auditable records and the finalized rules in Document 05. Version 1 must not introduce undocumented adjustment fields or manual balance overrides.

## 8. `FeeObligations` tab

**Purpose:** Represent a charge or installment owed by a student. Payments are separate records allocated to these obligations.

| # | Column | Type | Required | Rules |
|---:|---|---|---|---|
| 1 | `fee_obligation_id` | String | Yes | Unique, immutable ID |
| 2 | `student_id` | String | Yes | References `Students.student_id` |
| 3 | `enrollment_id` | String | No | Must belong to the same student when present |
| 4 | `package_id` | String | No | Must belong to the same student when present |
| 5 | `obligation_description` | String | Yes | Clear description of the charge/installment |
| 6 | `amount_due` | Number | Yes | Non-negative monetary amount |
| 7 | `currency` | String | Yes | `INR` in Version 1 |
| 8 | `issue_date` | Date | No | Date obligation was issued |
| 9 | `due_date` | Date | No | Due date, if applicable |
| 10 | `obligation_status` | Enum | Yes | `OPEN`, `PARTIALLY_PAID`, `PAID`, `VOID` |
| 11 | `notes` | String | No | Optional context |
| 12 | `created_at` | Timestamp | Yes | Set by backend |
| 13 | `updated_at` | Timestamp | Yes | Set by backend |
| 14 | `voided_at` | Timestamp | No | Set when voided |
| 15 | `void_reason` | String | No | Required when voided |

Rules:

- The student reference is mandatory.
- Optional enrollment and package references must belong to the same student.
- `amount_due` cannot be negative.
- `PAID` and `PARTIALLY_PAID` are derived states and must be reconciled against valid payment allocations.
- An obligation is overdue when its due date is before the current local calendar date and its outstanding amount is greater than zero, provided it is not void.
- A `VOID` obligation does not contribute to outstanding balances.
- Voiding requires a reason and an audit entry.
- The backend must define how overpayments are handled. It must not silently clamp a real credit or overpayment into an unexplained zero balance.

Derived values (not manually maintained authoritative columns):

- `paid_amount = sum(valid allocated payments for the obligation)`
- `outstanding_amount = amount_due - paid_amount`, subject to the finalized credit/overpayment policy
- `is_overdue = due_date < today_in_Asia/Kolkata AND outstanding_amount > 0 AND obligation_status != VOID`

## 9. `Payments` tab

**Purpose:** Chronological record of received payments. Do not overwrite prior payment rows to represent a new transaction.

| # | Column | Type | Required | Rules |
|---:|---|---|---|---|
| 1 | `payment_id` | String | Yes | Unique, immutable ID |
| 2 | `student_id` | String | Yes | References `Students.student_id` |
| 3 | `fee_obligation_id` | String | Yes | References a valid, non-void `FeeObligations.fee_obligation_id` belonging to the same student; mandatory for all payments in Version 1. Unallocated payments, advance payments, and unallocated credits are explicitly out of scope |
| 4 | `payment_date` | Date | Yes | Actual received date |
| 5 | `amount` | Number | Yes | Greater than zero for a normal receipt |
| 6 | `currency` | String | Yes | `INR` in Version 1 |
| 7 | `payment_method` | Enum | Yes | `UPI`, `BANK_TRANSFER`, `CASH`, `CARD`, `OTHER` |
| 8 | `transaction_reference` | String | No | Bank/UPI reference or internal receipt reference |
| 9 | `idempotency_key` | String | Yes | Unique idempotency key sent by client to deduplicate payment creation; stored with payment record |
| 10 | `payment_status` | Enum | Yes | `RECORDED`, `VOID` |
| 11 | `notes` | String | No | Optional context |
| 12 | `created_at` | Timestamp | Yes | Set by backend |
| 13 | `updated_at` | Timestamp | Yes | Set by backend |
| 14 | `voided_at` | Timestamp | No | Set when voided |
| 15 | `void_reason` | String | No | Required when voided |

Rules:

- A normal recorded payment must have a positive amount.
- Every payment must reference a valid, non-void fee obligation belonging to the same student with matching currency.
- Unallocated payments, advance payments, and unallocated credits are explicitly out of scope in Version 1.
- The payment amount must not exceed the remaining outstanding balance of the obligation.
- `VOID` payments remain visible in history but do not count toward paid totals.
- Correcting a payment requires an auditable void/correction workflow; normal UI operations must not silently delete it.
- `idempotency_key` is required on creation and stored directly with the payment record in the spreadsheet. Do not rely only on disabling the frontend button or on an audit entry being written afterward.
- A retry with the same `idempotency_key` and equivalent payload must return the original outcome. Reusing the key with a materially different payload must return a conflict error.
- Refunds and chargebacks are not represented as ordinary positive receipts. If required, they need an explicit documented transaction model.
- Payment allocation and overpayment policy are defined in Document 05.

## 10. `ClassSessions` tab

**Purpose:** Record scheduled and historical one-on-one class sessions.

| # | Column | Type | Required | Rules |
|---:|---|---|---|---|
| 1 | `class_session_id` | String | Yes | Unique, immutable ID |
| 2 | `student_id` | String | Yes | References `Students.student_id` |
| 3 | `enrollment_id` | String | No | Must belong to the same student when present |
| 4 | `package_id` | String | No | Must belong to the same student when present |
| 5 | `meeting_link_id` | String | No | Must reference an existing link belonging to the same student |
| 6 | `class_title` | String | Yes | Human-readable class/session title; frontend supplies a default such as 'Class session' if left blank by the administrator |
| 7 | `scheduled_start` | Timestamp | Yes | Scheduled start time |
| 8 | `scheduled_end` | Timestamp | Yes | Must be after scheduled start; UI calculates and persists end timestamp when duration is entered |
| 9 | `actual_start` | Timestamp | No | Actual start, if recorded |
| 10 | `actual_end` | Timestamp | No | Actual end, if recorded |
| 11 | `session_status` | Enum | Yes | `SCHEDULED`, `COMPLETED`, `CANCELLED`, `RESCHEDULED`, `NO_SHOW` |
| 12 | `attendance_status` | Enum | Yes | `NOT_MARKED`, `ATTENDED`, `ABSENT`, `EXCUSED` |
| 13 | `class_credit_effect` | Enum | Yes | `PENDING`, `CONSUME`, `NO_CONSUME`, `CREDIT_BACK` |
| 14 | `cancellation_reason` | String | No | Reason when applicable |
| 15 | `credit_restoration_for_session_id` | String | Conditional | References `ClassSessions.class_session_id` of the original consumed session; mandatory when `class_credit_effect = CREDIT_BACK`, blank otherwise; unique across all restorations |
| 16 | `notes` | String | No | Optional session notes |
| 17 | `created_at` | Timestamp | Yes | Set by backend |
| 18 | `updated_at` | Timestamp | Yes | Set by backend |
| 19 | `completed_at` | Timestamp | No | Set when completion is confirmed |

Rules:

- `scheduled_end` must be after `scheduled_start`.
- Every session belongs to a student.
- Enrollment, package, and meeting-link references must belong to that student when supplied.
- `SCHEDULED` sessions do not consume a class (`class_credit_effect = PENDING`).
- The Version 1 class-credit policy is explicit and finalized:
  - `COMPLETED and attended`: Consume one credit (`CONSUME`) when linked to an eligible package.
  - `NO_SHOW`: No credit consumed by default (`NO_CONSUME`).
  - `ABSENT`: No credit consumed by default (`NO_CONSUME`).
  - `EXCUSED`: No credit consumed (`NO_CONSUME`).
  - `CANCELLED`: No credit consumed by default (`NO_CONSUME`); late cancellations are treated as `CANCELLED` under this default policy.
  - `RESCHEDULED`: No credit consumed by the superseded session (`NO_CONSUME`).
  - A completed session without an eligible package must not change any package balance (`NO_CONSUME`).
- `CREDIT_BACK`: When an audited correction restores a credit, a dedicated `ClassSessions` record is created with `class_credit_effect = CREDIT_BACK` and `credit_restoration_for_session_id` referencing the original consumed session. The original session preserves `class_credit_effect = CONSUME`. A given `credit_restoration_for_session_id` can appear at most once across all restorations, guaranteeing that the same consumed credit is never restored twice.
  - Field population: `class_title` is set to `"Credit Restoration: " + original_title` (or default `"Credit Restoration"`), `scheduled_start` and `scheduled_end` are both set to the restoration timestamp (zero duration), `session_status = COMPLETED`, `attendance_status = NOT_MARKED`, `meeting_link_id` is blank, and `notes` contains the administrative reason.
  - Operational isolation: All schedule, calendar, upcoming session, and attendance queue queries MUST filter out `class_credit_effect = CREDIT_BACK`. Restoration records are visible only in the student package ledger and credit audit views.
  - Immutability: Restoration records are terminal; the backend rejects any requests to reschedule, cancel, or modify attendance on them.
- Deduplication strategy for class completion: Existing-state check, script locking, and single-credit-consumption protection ensure retried completions do not consume multiple credits.
- A completed session must have `completed_at` set.
- Rescheduling must preserve the prior scheduling change in the audit history and must not cause duplicate class consumption.

- `Enrollments.student_id` → `Students.student_id`
- `Packages.student_id` → `Students.student_id`
- `Packages.enrollment_id` → `Enrollments.enrollment_id`, when present
- `FeeObligations.student_id` → `Students.student_id`

- `FeeObligations.package_id` → `Packages.package_id`, when present

- `ClassSessions.student_id` → `Students.student_id`
- `ClassSessions.enrollment_id` → `Enrollments.enrollment_id`, when present
- `ClassSessions.package_id` → `Packages.package_id`, when present

- `ClassSessions.credit_restoration_for_session_id` → `ClassSessions.class_session_id` (mandatory when `class_credit_effect = CREDIT_BACK`; references original session with `CONSUME` for same student and package; unique across all restorations)

- `ImportRowResults.import_batch_id` → `ImportBatches.import_batch_id`

For every optional relationship, if a reference is supplied, the referenced record must exist and belong to the same student where that ownership rule applies. Checking only that an ID exists is insufficient.

## 18. Derived values and source of truth

The following values are derived and must not be manually edited as authoritative totals:

- Student outstanding fees: sum of valid fee-obligation outstanding amounts.
- Fee obligation paid amount: sum of valid allocated payments.
- Fee obligation outstanding amount: amount due minus valid allocated payments, subject to the explicit credit policy.
- Package remaining classes: purchased allocation minus valid consumption plus valid class credits.
- Overdue status: derived from due date, outstanding balance, and obligation status.
- Dashboard counts: derived from canonical records and documented filters.

If performance later requires materialized summaries, they must be treated as rebuildable caches with reconciliation tests, never as independent truth.

## 19. Schema validation and initialization

The backend must provide a controlled schema health check that verifies:

- Every required tab exists.
- Every required header exists exactly once.
- Header names are not duplicated.
- The supported schema version is present.
- Required configuration values are valid.
- The spreadsheet is the configured spreadsheet, not an arbitrary ID supplied by a client.

A missing required header must cause a clear health-check failure. The system must not silently interpret a missing column as an empty field.

Initialization may create a new spreadsheet's tabs and headers through an explicit setup operation. It must not automatically reshape or delete columns in a live spreadsheet.

## 20. Performance rules

Google Sheets is not a relational database and does not provide database indexes or full multi-table transactions. The backend must therefore:

- Read ranges in batches.
- Build temporary ID maps for repeated lookups during a request.
- Avoid reading every tab for every UI operation.
- Avoid one read/write operation per cell.
- Use bounded results for list/search APIs.
- Use locks for critical mutations where concurrent execution could corrupt state.
- Re-read relevant records inside the lock before committing a state-dependent mutation.
- Minimize partial writes across related records and define recovery behavior where atomicity is unavailable.
- Keep caches optional, short-lived where appropriate, and explicitly invalidated after writes.

No unsupported student-count capacity claim should be made. Performance must be tested against realistic data volume and expected usage.

## 21. Schema changes

Every schema change requires:

1. A documented reason and requirement.
2. The previous and new schema versions.
3. An explicit migration procedure.
4. Tests against existing records.
5. A recovery or rollback plan.
6. Updates to the API, business rules, tests, and agent instructions where affected.

The implementation agent must not independently rename columns, change enum values, remove fields, or add undocumented fields.

## 22. Acceptance criteria

The data model is accepted when:

- All twelve canonical tabs and their headers are defined and validated.
- IDs remain stable when rows are sorted or moved.
- Foreign-key and same-student ownership checks are enforced server-side.
- Payment history is retained and balances are reproducible.
- Class consumption is derived from explicit session outcomes and policy.
- Multiple meeting links can be stored for one student.
- Inactive students retain all related history.
- Imports provide row-level reconciliation results.
- Missing or duplicate headers produce explicit errors.
- No routine operation hard-deletes historical financial or class records.
